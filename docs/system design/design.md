## Задача

Проектируем центральный сервис идентификации (IdP/SSO): пользователь аутентифицируется один раз и работает во всех подключённых приложениях. Приложения - клиенты нашей системы.

## Требования

Требуется система SSO уровня "Production-ready" в плане качества решений и обоснований. Проектирование должно опираться на спецификации OAuth 2.1 и OIDC.

### Функциональные требования

**В скоупе (FR):**

- Пользователь может зарегистрироваться в системе;
- Пользователь может предоставить согласие на определенный список прав для клиента (consent screen);
- Пользователь может подтвердить свой email после успешной регистрации;
- Пользователь может залогиниться под своим аккаунтом в системе;
- Пользователь может выйти из своего аккаунта, завершив сессию (RP-initiated logout - убивается сессия и все семьи refresh-токена пользователя, получается единый logout);
- Пользователь может сменить свой пароль (с доступом к своему аккаунту);
- Пользователь может восстановить пароль через email (происходит процедура смены пароля без прямого доступа к аккаунту пользователя);

- Пользователь может посмотреть свой профиль в системе;
- Пользователь может изменить информацию в своем профиле;
- Пользователь может посмотреть свои последние действия в системе за последние 7 дней (регистрация,  подтверждение email, логин, выход, подключение клиентов к аккаунту, отзыв аккаунта от клиента, изменение информации в профиле, смена пароля, восстановление пароля);
- Пользователь может посмотреть список клиентов, к которым подключен данный аккаунт;
- Пользователь может отозвать доступ к своему аккаунту для конкретного клиента;

- Пользователь, уже аутентифицированный на сервере, может подключить свой аккаунт к новому клиенту и получать в нём токены без повторного ввода пароля (тихая ре-аутентификация);
- Пользователь или клиент может запросить токены (access, refresh, опционально id_token при scope openid);
- M2M-клиент может запросить только access-токен с использованием гранта client credentials;
- Клиент может запросить обновление токенов с помощью refresh-токена;
- Клиент может получить публичные ключи сервера (JWKS);
- Клиент может проверить доступ к запрашиваемому ресурсу по токену.

**Вне скоупа:** MFA и SAML, соцлогины, админ-функции (бан/деактивация), удаление аккаунта.

### Нефункциональные требования

- 50 млн зарегистрированных пользователей;
- 5 млн DAU;
- 20 приложений-клиентов;

- В среднем 50 тыс/день регистраций новых пользователей;
- В среднем пользователь логиниться 1.2 раза в день;
- Средняя активная сессия пользователя ~75 мин/день;
- Время жизни сессии на сервере без обновления 12 часов, максимум 7 дней (скользящая);
- В среднем 10 тыс/день восстановлений пароля;

- В среднем пользователь смотрит свой профиль 0.1 раз в день;
- В среднем пользователь смотрит ленту своих последних действий 0.1 раз в день;
- В среднем пользователь меняет информацию в своем профиле 0.01 раз в день;

- У пользователя в среднем 1.5 устройства на аккаунт;
- У пользователя в среднем подключено 2.5 клиента;
- У пользователя повторных тихих ре-аутентификаций ~2/день на клиента;

- Пиковые коэффициенты: логины x8 (утро/вечер), токен-операции x4;

- Доступность 99.9%;
- latancy логина/регистрации p99 <= 1 c;
- latancy валидации токена p99 <= 50 мc;

- TTL access 5 мин;
- TTL refresh 7 дней;

- Информацию о действиях пользователя храним 1 год;
- Период ротации ключей подписи JWKS = 30 дней;

- refresh с ротацией и детекцией переиспользования;
- Естественное истечение сессии на сервере (12 ч без обновления или 7 дней) не отзывает семьи refresh-токена. Естественное истечение семьи refresh-токена не влияет на сессию на сервере (при этом события отзыва работают по прежней логике);

- хранение токенов на клиенте;
- Размер токена ~5 КБ.

### Прикидка нагрузки

**Подсчет RPS:**

- RPS при регистрации: `50 тыс / 86400 ≈ 0.6 RPS`;

- RPS при логине: `(5 млн x 1.2) / 86400 ≈ 70 RPS (в пике 70 x 8 = 560 RPS)`;

- RPS при восстановлении пароля: `10 тыс / 86400 ≈ 0.1 RPS`;

- RPS при выходе из системы:
  
  Примем как допущение, что `10%` логинов в среднем оканчивается ручным выходом из системы пользователем. Тогда получаем: `70 RPS x 10% = 7 RPS (в пике 7 x 8 = 56 RPS)`;

- RPS при просмотре профиля: `(5 млн x 0.1) / 86400 ≈ 6 RPS`;

- RPS при просмотре ленты активности: `(5 млн x 0.1) / 86400 ≈ 6 RPS`;

- RPS при изменении профиля: `(5 млн x 0.01) / 86400 ≈ 0.6 RPS`;

- RPS при обновлении access-токена с помощью refresh-токена: `5 млн x 75 мин/день / 5 мин / 86400 ≈ 900 RPS (в пике 900 x 4 = 3600 RPS)`;

- RPS при тихой ре-аутентификации: `5 млн x 2.5 клиента x 2 / 86400 ≈ 300 (в пике 300 x 4 = 1200 RPS)`;

- RPS на получение токенов для M2M-клиентов:
  
  Примем как допущение число M2M-клиентов = `5 из всего 20 клиентов`. У каждого M2M-клиента будет в среднем по 500 воркер-инстансов. Тогда при кэшировании токена до истечения TTL получаем: `5 x 500 / 5 мин / 60 = 8 RPS`;

Так как несколько сценариев работают через один эндпоинт, например, `/token` принимает refresh-гранты, M2M и обмен кода на токены после логина и тихой auth, `/authorize` - редиректы логинов и тихие ре-аутентификации. В таком случае можно посчитать общую нагрузку так же и по эндпоинтам:

- `/token`: `900 + 8 + 70 + 300 ≈ 1300 RPS (в пике 3600 + 8 + 560 + 1200 ≈ 5400 RPS)`;
- `/authorize`: `300 + (70 x 2) = 440 RPS (в пике 1200 + (560 x 2) ≈ 2300 RPS)`.

Опциональные потоки (смена пароля, клики подтверждения email, JWKS) можно оставить за скобками - они на порядки меньше крупных.

**Подсчет CPU:**

**Метод:** для каждой статьи - `ядра = RPS потока × мс CPU одной операции / 1000`. Считаем среднее и пик раздельно, итоговый объем бронируем под пик.

- Хеширование пароля (доминант по потреблению):
  
  Для хеширования пароля предлагается использовать криптографический алгоритм **Argon2id**. При конфигурации с хорошей безопасностью `m = 64 МБ, t = 3, p = 4` примерное время выполнения `~100-200 мс` и потребление памяти `64 МБ`.
  
  Таким образом, необходимое количество ядер для хэширования пароля: `70 + 0.6 + 0.1 RPS x 200 мс x 4 / 1000 ≈ 57 (в пике 560 + 4.8 + 0.8 x 200 мс x 4 / 1000 ≈ 450)`. А потребление памяти будет: `70 + 0.6 + 0.1 RPS x 200 мс / 1000 x 64 МБ ≈ 905 МБ (в пике 560 + 4.8 + 0.8 x 200 мс / 1000 x 64 МБ ≈ 7.2 ГБ)`.

- Подпись токенов:
  
  Для подписи токенов предлагается использовать алгоритм **EdDSA** (Ed25519), который выполняется примерно за `~20 мкс`.
  
  Таким образом, необходимое количество ядер для подписи токенов: `1300 RPS x 20 мкс x 2 / 1000000 = 0.052 (в пике 5400 x 20 мкс x 2 / 1000000 = 0.2)`. Даже в пике получается пренебрежимо малое число. 
  
- Прочие операции:
  
  Генерация кодов и opaque-токенов (urandom), JSON-сериализация, Redis-операции (это IO, а не CPU), аудит (async-запись, IO), TLS (обычно терминируется на балансировщике - за скобками). Все в сумме не имеет какой-либо существенной нагрузки: `5400 + 2300 + 56 (logout) + ~110 (профиль/лента/правки/регистрация/восстановление ×8) RPS x 5 мс (пессимистичная верхняя граница) / 1000 ≈ 40`.

Если взять как допущение, что один инстанс сервера имеет `32 ядер`, тогда необходимо взять `450 + 40 + 0.2 ядер / 32 ≈ 16 инстансов сервера`, с запасом в итоге возьмем `22 инстансов сервера`, учитывая `≤70%` утилизации пика. N+1 проходит с запасом: после потери инстанса `21 × 32 = 672 ≥ 490`.

**Подсчет объема хранения:**

Сделаем допущение, что сущности имеют следующие размеры:

| Сущность                         | Хранилище                   | Размер записи             | Из чего складывается                                               |
| -------------------------------- | --------------------------- | ------------------------- | ------------------------------------------------------------------ |
| Аккаунт                          | RDBMS                       | `1–2 КБ`                  | email ~100 Б + хеш пароля ~100 Б + профиль/флаги/даты              |
| Аватар аккаунта                  | object storage              | `200-300 КБ`              | сжатое изображение, например webp/jpeg 512×512                     |
| Консент                          | RDBMS                       | `~200 Б`                  | user×client, scopes, дата                                          |
| Сессия сервера                   | KV (Redis Cluster)          | `1–2 КБ`                  | sid, user, device/IP/UA, метки idle/absolute, подключённые клиенты |
| Refresh-грант                    | KV (Redis Cluster) + журнал | `0.3–0.5 КБ`              | SHA-256 токена 32 Б, family/user/client, счётчики reuse, TTL       |
| Код авторизации                  | KV (Redis Cluster)          | `~0.5 КБ, TTL минуты`     | код, client, redirect_uri, PKCE challenge                          |
| Email-токен (verify/reset)       | KV (Redis Cluster)          | `~0.5 КБ, TTL часы`       | хеш токена, user                                                   |
| Аудит-событие (лента активности) | append-only хранилище       | `~0.5 КБ JSON, до сжатия` | actor, действие, ip/ua, время                                      |
| Access JWT                       | не хранится                 | `0`                       | stateless — 5 КБ живут у клиента                                   |
| Ключ JWKS                        | RDBMS                       | `64 байта`                | Ed25519: 32+32 Б, ротация 30 дней                                  |

Тогда, учитывая окно жизни и количество записей, получаем общий объем по каждой сущности:

| Сущность                         | Окно жизни        | Количество записей                                                             | Размер                 | Объём                               |
| -------------------------------- | ----------------- | ------------------------------------------------------------------------------ | ---------------------- | ----------------------------------- |
| Аккаунты                         | жизнь аккаунта    | `50 млн`                                                                       | `2 КБ`                 | `50 млн x 2 КБ = 100 ГБ`            |
| Аватары аккаунта                 | жизнь аккаунта    | `50 млн x 30% (допущение покрытия аккаунтов аватарами) x 1 вариант = 15 млн`   | `~300 КБ`              | `15 млн x 300 КБ = 4.5 ТБ`          |
| Консенты                         | жизнь аккаунта    | `125 млн`                                                                      | `~200 Б`               | `125 млн x 200 Б = 25 ГБ`           |
| Сессии сервера                   | 12 ч              | `5 млн x 1.5 = 7.5 млн` от DAU                                                 | `1.5 КБ`               | `7.5 млн x 1.5 КБ = 11.3 ГБ`        |
| Refresh-гранты                   | скользящие 7 дней | `5 млн x 2.5 (коэффициент) x 1.5 устройства x 2.5 клиента = 46.875 млн` от DAU | `400 Б`                | `46.875 млн x 400 Б = 18.75 ГБ`     |
| Коды авторизации                 | минуты            | `370/с x 5 мин TTL = 111 тыс`                                                  | `0.5 КБ`               | `111 тыс x 500 Б = 55.5 МБ`         |
| Email-токены                     | часы              | `~60 тыс/день x 24 ч = 60 тыс`                                                 | `0.5 КБ`               | `60 тыс x 500 Б = 30 МБ`            |
| Аудит-события (лента активности) | 1 год             | `(70 + 7 + 0.6 + 0.6 + 0.6 + 0.1) RPS x 86400 ≈ 7 млн/день`                    | `0.5 КБ`               | `7 млн x 500 Б x 365 ≈ 1.28 ТБ/год` |
| Access JWT                       | —                 | 0 - stateless                                                                  | `5 КБ` живёт у клиента | 0                                   |
| Ключ JWKS                        | —                 | десятки байт                                                                   | —                      | `≈0`                                |

В итоге получим объемы хранения по каждому типу хранилища:

| Хранилище          | Сущности                         | Сырой объем                          | Множители                                          | Итоговый объём                                                                                                        |
| ------------------ | -------------------------------- | ------------------------------------ | -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| RDBMS              | аккаунты + консенты + JWKS       | `100 + 25 + 0 = 125 ГБ`              | индексы `x1.5` + репликация `x3`                   | `125 ГБ x 1.5 x 3 = 562,5 ГБ`                                                                                         |
| KV (Redis Cluster) | сессии + гранты + коды + email   | `11.3 + 18.75 + 0.06 + 0.03 ≈ 30 ГБ` | `50-100 Б` на ключ + AOF `x1.75` + репликация `x3` | `(30 ГБ + (~54.5 млн ключей x 100 Б)) x 1.75 x 2 ≈ 186 ГБ`                                                            |
| Object storage     | аватары                          | `4.5 ТБ`                             | managed (S3-подобное) `x1`                         | `4.5 ТБ`                                                                                                              |
| Append-only        | аудит-события (лента активности) | `1.28 ТБ/год`                        | сжатие холодных записей `x1/3` + репликация `×3`   | `~24 ГБ (горячие записи за 7 дней) x 3 реплики + 1.22 ТБ/год (холодные записи) / 4 (сжатие) x 3 реплики = 987 ГБ/год` |

В итоге, суммарный объём `~6.2 ТБ`, из них:
- object storage - `4.5 ТБ` (~73%);
- append-only хранилище - `~1 ТБ/год` (~16%);
- RDBMS `~0.56 ТБ` (~9%);
- KV (Redis Cluster) `~0.186 ТБ` (~2%).

Прирост объёма получается всего `~2.7 ТБ/год`, из них:
- object storage - `~1.6 ТБ/год`;
- append-only хранилище - `~1.28 ТБ/год`;
- RDBMS - `~36 ГБ/год`.

Рост почти целиком уходит в object storage. RDBMS и KV практически не растут.
