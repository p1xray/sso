## Задача

Проектируем центральный сервис идентификации (IdP/SSO): пользователь аутентифицируется один раз и работает во всех подключённых приложениях. Приложения - клиенты нашей системы.

## Требования

Требуется система SSO уровня "Production-ready" в плане качества решений и обоснований. Проектирование должно опираться на спецификации OAuth 2.1 и OIDC.

### Функциональные требования

**В скоупе (FR):**

- Пользователь может зарегистрироваться в системе;
- Пользователь может предоставить согласие на определенный список прав для клиента (consent screen);
- Пользователь может подтвердить свой email после успешной регистрации;
- Пользователь может залогиниться под своим аккаунтом в системе;
- Пользователь может выйти из своего аккаунта, завершив сессию (RP-initiated logout - убивается сессия и все семьи refresh-токена пользователя, получается единый logout);
- Пользователь может сменить свой пароль (с доступом к своему аккаунту);
- Пользователь может восстановить пароль через email (происходит процедура смены пароля без прямого доступа к аккаунту пользователя);

- Пользователь может посмотреть свой профиль в системе;
- Пользователь может изменить информацию в своем профиле;
- Пользователь может посмотреть свои последние действия в системе за последние 7 дней (регистрация,  подтверждение email, логин, выход, подключение клиентов к аккаунту, отзыв аккаунта от клиента, изменение информации в профиле, смена пароля, восстановление пароля);
- Пользователь может посмотреть список клиентов, к которым подключен данный аккаунт;
- Пользователь может отозвать доступ к своему аккаунту для конкретного клиента;

- Пользователь, уже аутентифицированный на сервере, может подключить свой аккаунт к новому клиенту и получать в нём токены без повторного ввода пароля (тихая ре-аутентификация);
- Пользователь или клиент может запросить токены (access, refresh, опционально id_token при scope openid);
- M2M-клиент может запросить только access-токен с использованием гранта client credentials;
- Клиент может запросить обновление токенов с помощью refresh-токена;
- Клиент может получить публичные ключи сервера (JWKS);
- Клиент может проверить доступ к запрашиваемому ресурсу по токену.

**Вне скоупа:** MFA и SAML, соцлогины, админ-функции (бан/деактивация), удаление аккаунта.

### Нефункциональные требования

- 50 млн зарегистрированных пользователей;
- 5 млн DAU;
- 20 приложений-клиентов;

- В среднем 50 тыс/день регистраций новых пользователей;
- В среднем пользователь логиниться 1.2 раза в день;
- Средняя активная сессия пользователя ~75 мин/день;
- Время жизни сессии на сервере без обновления 12 часов, максимум 7 дней (скользящая);
- В среднем 10 тыс/день восстановлений пароля;

- В среднем пользователь смотрит свой профиль 0.1 раз в день;
- В среднем пользователь смотрит ленту своих последних действий 0.1 раз в день;
- В среднем пользователь меняет информацию в своем профиле 0.01 раз в день;

- У пользователя в среднем 1.5 устройства на аккаунт;
- У пользователя в среднем подключено 2.5 клиента;
- У пользователя повторных тихих ре-аутентификаций ~2/день на клиента;

- Пиковые коэффициенты: логины x8 (утро/вечер), токен-операции x4;

- Доступность 99.9%;
- latancy логина/регистрации p99 <= 1 c;
- latancy валидации токена p99 <= 50 мc;

- TTL access 5 мин;
- TTL refresh 7 дней;

- Информацию о действиях пользователя храним 1 год;
- Период ротации ключей подписи JWKS = 30 дней;

- refresh с ротацией и детекцией переиспользования;
- Естественное истечение сессии на сервере (12 ч без обновления или 7 дней) не отзывает семьи refresh-токена. Естественное истечение семьи refresh-токена не влияет на сессию на сервере (при этом события отзыва работают по прежней логике);

- хранение токенов на клиенте;
- Размер токена ~5 КБ.
