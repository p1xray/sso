# ADR: `backend/pkg/postgresql`

## Статус

Принят и реализован (сентябрь 2026). Пакет: `github.com/p1xray/sso/backend/pkg/postgresql`, Go 1.27, внешняя зависимость: `github.com/jackc/pgx/v5`.

## Контекст:

Единая обёртка над пулом соединений PostgreSQL для Go-сервисов поверх `pgxpool` (`github.com/jackc/pgx/v5/pgxpool`).

### Требования:

- Сервис не стартует, пока БД недоступна (ping-retry с backoff);
- Точки перехвата: логирование и метрики добавляются в обёртке, а не в прикладном коде;
- Логирование запросов для локальной отладки;
- DI без глобального состояния - конфигурация целиком извне.

### Альтернативы:

- Прямой `*pgxpool.Pool` в каждом сервисе - нет точек перехвата, ping-retry дублируется;
- `database/sql`/`sqlx` - потеря нативных возможностей pgx (COPY, batches, `pgx.Tx`);
- Репозиторный слой в сервисах сразу - преждевременно, пока схема данных не устоялась.

### Non-goals:

Миграции, ORM/query-builder, репозиторный паттерн, шардирование и реплики - вне пакета: он только владеет пулом и проксирует операции.

## Ключевые архитектурные решения

### 1. Запечатанный интерфейс `Postgres` над приватным пулом

`*pgxpool.Pool` приватен, наружу - интерфейс `Postgres` с делегирующими методами: `Exec`/`Query`/`QueryRow`, транзакции `Begin`/`BeginTx`/`BeginFunc`, `CopyFrom`, `Ping`, `Stat`, `Close`. Смысл - точки перехвата: любая фича (логирование запросов, метрики, роутинг на реплику) добавляется в делегатах, прикладной код не меняется. `Unwrap()` возвращает сырой пул - escape-hatch для `main`-обвязки, симметрично `Unwrap()` в `logger` (см. [0001](0001-logger-package.md)). Контракт зафиксирован compile-time проверкой `var _ Postgres = (*postgres)(nil)`.

### 2. `New` - единственная точка создания

`New(ctx, connString, opts ...Option)`: `pgxpool.ParseConfig` → опции → `pgxpool.NewWithConfig` → `pingWithRetry`. Провал ping закрывает пул и возвращает ошибку - сервис честно падает на старте, а не стартует «вслепую». `pingWithRetry`: до 10 попыток по умолчанию, экспоненциальный backoff с jitter. Каждая ping-попытка ограничена `maxBackoff`, весь цикл отменяется через `ctx`.

### 3. Конфигурация через functional options

`ConnAttempts` (дефолт 10), `ConnAttemptTimeout` (дефолт 1s - начальная задержка, удваивается до потолка), `MaxBackoff` (дефолт 10s - потолок и задержки, и длительности каждой попытки), `LogQueries`, `LogPingAttempts`. Каждая опция валидирует аргумент и возвращает ошибку. Пакет не читает env и не держит глобального состояния.

### 4. Логирование запросов через pgx Tracer

`LogQueries` ставит `loggerTracer` в `ConnConfig.Tracer`: начало запроса - info с SQL и аргументами, конец запроса - при ошибке - error, успешное завершение не логируется. Зависимость - только на интерфейс `logger.Logger`, не на конкретную реализацию.

## Интересные моменты реализации

- Jitter масштабирует задержку в `[0.5, 1)` - флот сервисов, стартующих одновременно, не ретраит синхронно (`math/rand/v2`, без seed).
- Задержка удваивается, только пока ниже `maxBackoff`. Достигнув потолка, цикл продолжает с ним же.
- `SendBatch` реализован на конкретном типе, но пока не входит в контракт `Postgres` - интерфейс запечатан (одна реализация), расширяется по мере надобности.
- Тесты: валидация опций, потолок backoff (по wall-clock: 3 попытки с `ConnAttemptTimeout(1h)` + `MaxBackoff(20ms)` укладываются в секунду), warning о недоступной БД. Интеграционный сценарий `QueryRow`/`BeginFunc`/`Tracer` под `TEST_POSTGRESQL_DSN`.

## Возможные улучшения

1. **Метрики пула** - `Stat()` (acquire waits, total/idle/max conns) в Prometheus.
2. **Duration в query-логах** - `TraceQueryEndData` содержит `StartTime`, логировать длительность медленных запросов, а не только ошибки.
3. **OTel-tracing** - второй Tracer в цепочке (`pgx.CompositeTracer`), без правок прикладного кода.
4. **Readiness-проба** - `Ping` как readiness/liveness-эндпоинт сервисов.
