# ADR: `backend/pkg/grpcserver`

## Статус

Принят и реализован (сентябрь 2026). Пакет: `github.com/p1xray/sso/backend/pkg/grpcserver`, Go 1.27, внешняя зависимость: `google.golang.org/grpc`.

## Контекст:

Единая обёртка над `google.golang.org/grpc` для gRPC-сервисов монорепо (`auth`, `oidc`, `users`, `clients`): создание сервера, регистрация сервисов, жизненный цикл с уведомлением о падении.

### Требования:

- DI без глобального состояния - конфигурация целиком извне, конвенции `postgresql` (см. [0002](0002-postgresql-package.md));
- Гарантированная остановка: graceful, но с потолком по времени - сервис обязан завершаться, даже если клиенты держат соединения;
- Сигнал о падении сервера (занятый порт, ошибка serve) наружу - сервис падает на старте, а не работает впустую;
- Точки перехвата для grpc-опций (TLS, keepalive, лимиты, интерцепторы) без открытия всего `*grpc.Server` в прикладной код.

### Альтернативы:

- Голый `*grpc.Server` в каждом сервисе - жизненный цикл (notify-канал, graceful-таймаут, защита от двойного старта) дублируется;
- Готовая обёртка - лишняя зависимость ради ~150 строк, API не под конвенции репо;
- Своя функция регистрации сервисов вместо `grpc.ServiceRegistrar` - потеря совместимости с генерируемым protoc-кодом.

### Non-goals:

Интерцепторы (логирование, recovery, auth), health-проба (`grpc_health_v1`), reflection, TLS-обвязка - вне пакета: подключаются через `WithGRPCOptions` или принимаются отдельными решениями.

## Ключевые архитектурные решения

### 1. Запечатанный интерфейс `Server` над приватным `*grpc.Server`

`*grpc.Server` приватен, наружу - интерфейс `Server`: `Start`, `Stop`, `Notify`, `Registrar` (цель для `RegisterXServer` из генерируемого кода) и `Unwrap` - escape-hatch, симметрично `logger` и `postgresql` (см. [0001](0001-logger-package.md), [0002](0002-postgresql-package.md)). Контракт зафиксирован compile-time проверкой `var _ Server = (*server)(nil)`.

### 2. Жизненный цикл и семантика Notify

`New(opts ...Option) (*server, error)` - единственная точка создания: опции → проверка адреса → `grpc.NewServer`. `Start` слушает и обслуживает в фоновой goroutine и падает только при повторном вызове (`started.CompareAndSwap` - вместо panic от двойного close). Исход serve доставляется через `Notify() <-chan error`: `nil` - штатная остановка, ошибка - авария (занятый порт, падение serve); после доставки канал закрывается. Канал буферизован (cap 1) - отправитель не блокируется без читателя, значение дожидается в буфере.

Гонка «`Stop` успел раньше, чем goroutine дошла до `Serve`» не подсовывает ложную аварию: grpc возвращает `ErrServerStopped`, который при выставленном флаге `stopRequested` заменяется на `nil`.

### 3. Graceful-остановка по таймауту и связь с ConnectionTimeout

`Stop` идемпотентен (`stopRequested.CompareAndSwap`): запускает `GracefulStop` и ждёт его либо истечения `shutdownTimeout` (дефолт 10s), после чего выполняет жёсткий `Stop()` и дожидается goroutine - метод гарантированно возвращается.

Нюанс grpc: `stop()` ждёт в `serveWG` не только accept-цикл, но и goroutine handshake каждого соединения, а их read-deadline задаёт `ConnectionTimeout` с дефолтом 120s - с «молчаливым» соединением (TCP открыт, HTTP/2-preface не отправлен) не завершается даже жёсткий stop. Поэтому `New` инжектит `grpc.ConnectionTimeout(shutdownTimeout)` как дефолт: handshake не может пережить shutdown-таймаут, и потолок `Stop` честен. Опция добавляется первой, так что пользовательский `grpc.ConnectionTimeout` через `WithGRPCOptions` перебивает её; задирать его выше shutdown-таймаута не стоит.

### 4. Опции с валидацией

`Option func(*server) error`, ошибка опции проваливает `New` (конвенция опций `postgresql`). `WithAddress` - обязателен, проверяется на непустоту и форму `host:port` (`net.SplitHostPort`); заменяет хардкод пустого host - адрес теперь управляет и интерфейсом бинда. `WithShutdownTimeout` - только положительный. `WithGRPCOptions` - проход `grpc.ServerOption` (TLS, keepalive, лимиты, интерцепторы) без их дублирования в пакете. `WithLogger` - отклоняет nil, nil-логгер задаётся отсутствием опции. Ошибки оборачиваются префиксом `grpcserver:`.

### 5. Логирование жизненного цикла

Опционально через `logger.Logger`: старт - info с атрибутом `addr`, ошибки listen/serve - error с `sl.Err`. Логгер не задан (по умолчанию) - жизненный цикл молчит; зависимость - только на интерфейс, не на реализацию (см. [0001](0001-logger-package.md)).

## Интересные моменты реализации

- Исход serve пишется в канал один раз в конце goroutine и всегда (`defer close`) - повторное чтение `Notify` после доставки даёт закрытый канал, а не блокировку.
- Тесты: валидация опций и `New` без адреса; жизненный цикл (тишина `Notify` пока жив, `nil` после `Stop`, закрытый канал); двойной `Start`; занятый порт (чужой listener) с ошибкой `grpcserver: failed to listen`; `Stop` сразу после `Start` (гонка с `ErrServerStopped`); потолок остановки - сырой TCP-коннект без preface + `WithShutdownTimeout(50ms)`, `Stop` обязан вернуться быстро. Всё под `-race`. Логирование - через logger с JSON-буфером.
- pkg→pkg зависимость на `logger` резолвится через `go.work` без `require` в `go.mod` - модуль ещё не опубликован, прецедент `postgresql`.

## Возможные улучшения

1. **Интерцепторы** - logging/recovery-цепочки отдельными pkg, подключение через `WithGRPCOptions`.
2. **Health-проба** - `grpc_health_v1` как опция, readiness для оркестратора.
3. **Метрики** - активные соединения и состояние сервера через `stats.Handler`.
4. **Reflection для локальной отладки** - опция, выключенная по умолчанию.
